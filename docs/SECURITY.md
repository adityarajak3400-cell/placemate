# Security Requirements — PlaceMate

| | |
|---|---|
| **Version** | 1.0 |
| **Related** | `ARCHITECTURE.md`, `TEST_PLAN.md` |

> Security is a requirement of every task, not a phase before deployment. Every item below has a corresponding check in `TEST_PLAN.md` §8.

---

## 1. Authentication

- All `/api/*` routes except `/api/auth/signup`, `/api/auth/login`, `/api/health` require a valid JWT in `Authorization: Bearer <token>`.
- Passwords hashed with **bcrypt** (cost factor 10). Plaintext passwords are never logged, stored, or returned.
- Login failures return a **generic** `"Invalid credentials"` — never reveal whether the email exists.
- JWT payload contains only `{ userId, role }` — no email, no name, no sensitive data. Signed with `JWT_SECRET` (≥ 32 random chars, different per environment).
- Tokens expire (`JWT_EXPIRES_IN`); the client treats any 401 as "log out and redirect to login".
- Signup accepts only `STUDENT` or `RECRUITER` roles. `ADMIN` cannot be self-assigned through any API.

## 2. Authorization (role × resource matrix)

| Resource / Action | STUDENT | RECRUITER | ADMIN |
|---|---|---|---|
| Read own profile / update own profile | ✅ | — | — |
| Upload own resume | ✅ | — | — |
| List jobs | ✅ | ✅ | ✅ |
| Create job | ❌ | ✅ | ✅ |
| Read applicants of a job | ❌ | ✅ own jobs only | ✅ all |
| Apply to job | ✅ if eligible | ❌ | ❌ |
| Update application status | ✅ accept own offer only | ✅ own jobs only | ✅ all |
| View all applications / filters / export | ❌ | ❌ | ✅ |

**Ownership rules** (enforced in services, not just UI):

- Recruiters can only read/act on applications for jobs **they posted** (`job.postedById === userId`).
- Students can only read their **own** applications and profile.
- Any request for a resource the user doesn't own → `404` (existence-hiding) or `403`; never return foreign data.

## 3. Secrets

- Real values only in `server/.env` and `client/.env.local` — **both git-ignored**.
- `.env.example` contains keys with empty values, never real values.
- Anything in `NEXT_PUBLIC_*` is public by definition: only `NEXT_PUBLIC_API_URL` may go there. Cloudinary secret, JWT secret, DB URL never touch the client.
- Before every commit: `git status` + check the diff for accidental key pastes. If a secret ever lands in Git, rotate the key — deleting the commit is not enough.

## 4. Input Validation

- **Every** mutating endpoint validates body/query/params with zod **before** the controller runs (`validate(schema)` middleware).
- Reject unknown/extra fields; coerce and bound numbers (CGPA 0–10, batch range, page sizes).
- Query filters (admin list/export) are typed and allow-listed — an unparseable filter is a 400, not a passthrough.
- Prisma is used exclusively (parameterized queries). Raw SQL (`$queryRaw`) is forbidden without an ADR.

## 5. File Uploads (resume PDF)

- Multer `memoryStorage` + `limits: { fileSize: 5MB, files: 1 }`.
- MIME/extension check: `application/pdf` only → 400 otherwise.
- Filename from the client is never used on disk or in URLs; the Cloudinary public ID is generated by us (`resumes/<userId>-<timestamp>`).
- `pdf-parse` runs on the buffer; failures return a friendly 400, never a stack trace or a hang (timeout guard).
- Files are served from Cloudinary's domain, not our origin — no stored XSS via uploaded content.
- Uploaded file size is re-verified server-side even though the client also checks it.

## 6. Output & Error Handling

- Central Express error handler: logs full error server-side; responds with `{ error: { message } }` only. **No stack traces, no Prisma error internals in production.**
- Optional chaining on user input; escape/normalize before echoing anything back.
- React escapes by default — `dangerouslySetInnerHTML` is banned (job descriptions render as plain text with line breaks).

## 7. Transport & Headers

- `helmet` enabled on the API (sensible defaults).
- CORS: single allowed origin from `CLIENT_ORIGIN`; credentials disabled (JWT travels in the header).
- HTTPS everywhere in production (Vercel + Render do this automatically).
- Basic rate limiting (`express-rate-limit`) on `/api/auth/*` (e.g., 20 requests / 15 min / IP) and a global soft limit.

## 8. Database

- Single Prisma client singleton; all access through services (§Architecture rules).
- Least-privilege DB user (Supabase default user is scoped to the project database).
- No `SELECT *`-style overfetching in responses: services select only the fields the API contract requires (e.g., never return `passwordHash` — enforced by explicit `select`).
- Delete operations are scoped (`deleteMany` with ownership filter) — a bare `delete` on user-supplied ID is forbidden.

## 9. Frontend-Specific

- JWT is held in memory/localStorage (see ADR-004). Mitigations: no third-party scripts, no `dangerouslySetInnerHTML`, strict Content Security Policy later if needed. Upgrade path: httpOnly cookie via Next.js rewrite proxy (recorded in DECISIONS.md).
- Client-side route guards are UX only; the API independently enforces every rule.
- Role-based UI (hiding admin links) is cosmetic — the server is the source of truth.

## 10. Pre-Deployment Security Checklist

- [ ] `grep -ri "secret\|password\|api_key" client/src` returns nothing sensitive
- [ ] `.env` files not tracked (`git check-ignore server/.env client/.env.local` passes)
- [ ] Health endpoint leaks no version/build info
- [ ] Test with a STudent token hitting every recruiter/admin route (expect 403s)
- [ ] Test IDOR: student A requesting student B's application/profile
- [ ] Rate limit kicks in on repeated bad logins
- [ ] Production error responses contain no internals
- [ ] Supabase database password and Cloudinary keys are strong and unique
- [ ] Render/Vercel env vars set separately from local values
